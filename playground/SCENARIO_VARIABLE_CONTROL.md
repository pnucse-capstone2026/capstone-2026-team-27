# 시나리오별 변인통제 체크리스트

이 문서는 5개 이상탐지 시나리오 각각을 "공정하게 비교 가능한 실험"으로 만들기 위해
통제해야 할 변인을 정리한다. 목적은 **"탐지가 잘 됐다"는 결과가 진짜 이상탐지 로직
때문인지, 아니면 실험 설계상의 우연/편향 때문인지"를 구분**하는 것이다.

원칙(세션 전체에서 합의된 것):
- 퍼센트를 평균 내지 않고 원본 TP/FN/FP/TN부터 합산 후 재계산한다.
- 작은 n(특히 n≤13)에는 반드시 Clopper-Pearson 95% CI를 같이 보고한다.
- "이상 vs 정상"을 가르는 유일한 차이가 독립변인 하나여야 한다 — 나머지는 전부 통제.

---

## 0. 전 시나리오 공통 통제 변인

| 항목 | 통제 방법 | 확인 여부 |
|---|---|---|
| 리전 | 전부 `ap-northeast-2`(서울) | ✅ |
| 관측 윈도우 | 30포인트 × 300초 = 2.5시간 (`cloudwatch_client.py` 기본값) | ✅ |
| 반복 횟수(탐지 정확도) | 이상 5 + 정상 8 = n=13, 시나리오마다 동일 | ✅ (Lambda·S3·EC2좀비), ⏳(오버프로비저닝 측정 중), ❌(EDoS 미실측) |
| 반복 횟수(절감액/실행시간) | n≥1은 불충분 — 최소 n=3 (세션에서 "n=1 부족" 지적 후 확정) | ✅(S3), ✅(EC2좀비 5건), ❌(Lambda 계정한도로 막힘) |
| IForest 모델 버전 | `MOCK_SEED_BUFFER_FROZEN=True`로 동결 — 시나리오 간 모델이 달라지면 비교 불가 | ✅ 유지 중 (해제 시 전 시나리오 재측정 필요) |
| 신뢰구간 계산법 | Clopper-Pearson 정확 이항 (정규근사 아님) | ✅ |
| 승인 게이트 | 실제 정책은 안 건드림. 측정 전용 `--bypass-approval`/`bypass_approval_for_timing`만 사용, 결과 파일에 항상 라벨링 | ✅ |
| 독립 시행 원칙 | 같은 리소스에 여러 시행을 겹쳐 걸지 않음(겹치면 CloudWatch 지표가 합쳐져 n배 시행이 1개 시행이 됨) | ✅ (Lambda만 예외 — 리소스 1개 재사용이라 순차 실행으로 우회) |

## 0-1. 시나리오별 측정 파라미터 (워밍업 / 메트릭 주기)

"관측 윈도우 2.5시간"은 전부 공통이지만, **그 2.5시간을 어떻게 채우는지(워밍업 방식)**와
**CloudWatch에서 몇 초 간격으로 몇 개를 받아오는지**는 시나리오마다 다르다. 이 표는
그 구체적인 파라미터 값을 재현 가능하도록 기록한다.

| 시나리오 | 메트릭 주기(period_seconds) | 포인트 수(n_points) | 윈도우 길이 | 워밍업 방식 | 워밍업 소요시간 | CloudWatch 반영 대기 |
|---|---|---|---|---|---|---|
| ① 좀비 | 300초 | 30 | 2.5h | **없음** — 자연 방치, 나이가드(리소스 나이 ≥2.5h)로 대체 | 인스턴스 생성 후 2.5h 경과할 때까지 그냥 대기 | 별도 없음(나이가드 통과 시 바로 측정) |
| ② 오버프로비저닝 | 300초 | 30 | 2.5h | SSM duty-cycle 부하 **적극 발생**(목표 CPU%를 처음부터 끝까지 유지) | **2.5h(9000초) 전체** 부하 유지 필요 — 중간에 껐다 켜면 윈도우 앞부분이 왜곡됨 | 부하 종료 직후 바로 측정 가능(별도 대기 불필요, 이미 윈도우 내내 쌓임) |
| ③ 재시도폭증(Lambda) | 300초 | 30 | 2.5h | 마지막 `phase_minutes=15`분만 고에러율 호출 집중(27 baseline + 3 spike 구조) | 15분(짧은 스파이크로 충분 — 재시도폭증은 실시간성이 중요해 빠르게 반응하도록 설계) | `wait_sec=120`초(CloudWatch 지표 반영 대기) |
| ④ 대량다운로드(S3) | 300초 | 30 | 2.5h | 마지막 3개 구간(15분)만 GET 요청 집중, 나머지 27구간은 baseline 트래픽 | 15분 | `wait_sec=300`초 |
| ⑤ EDoS(AutoScaling) | 300초 | 30 | 2.5h(`baseline_minutes=150` 미만 금지) | desired_capacity를 처음부터 끝까지 anomaly capacity(3)로 유지 | `startup_wait_sec=600`초(인스턴스 기동) + `baseline_minutes=150`분(창 전체) | `metric_wait_sec=300`초 |

**핵심 차이 요약**:
- **①②(EC2 절대임계치 계열)**은 "윈도우 전체가 처음부터 끝까지 같은 상태"여야 판정되므로, 워밍업이 곧 측정 대상 상태 그 자체다(짧게 줄일 수 없음).
- **③④(짧은 스파이크형)**은 윈도우 뒷부분 15분만 이상 상태로 만들어도 Z-score persistence 조건(최근 3개 연속)을 충족한다 — 전체 워밍업 시간을 아낄 수 있음.
- **⑤(EDoS)**은 스크립트 자체 경고대로 `baseline_minutes`를 150분 밑으로 줄이면 창 앞부분이 0으로 채워져 탐지율이 낙관적으로 왜곡되므로 절대 단축 금지.

## 1. 좀비 (EC2, Stop)

- **독립변인**: CPU/네트워크 사용량 수준 (완전 유휴 vs 정상 사용)
- **통제 변인**:
  - 인스턴스 타입: t3.micro 13대 전부 동일
  - AMI / 보안그룹 / 서브넷: 전부 동일 (`ami-08d82cf148c92fcc3`, `sg-01eb420b11ed6706e`, `subnet-08c39c64faa7c9364`)
  - 유발 방식: "아무 작업도 안 시킴"(자연 방치) — 인위적 조작 없음
  - 나이가드: 인스턴스 나이가 윈도우 길이(2.5h) 이상이어야 측정 (신생 리소스 오탐 방지)
- **잠재 교란변수**:
  - 인스턴스별 부팅 시각 차이 → 나이가드로 이미 통제됨
  - t3.micro가 **최저 tier**라 Resize를 적용해도 절감액이 항상 $0 → 이 시나리오는 Stop만 검증하므로 무관하지만, 오버프로비저닝과 혼동하지 않도록 주의
- **실측 확인**: `triggered_metrics`가 5건 전부 `[cpu_utilization, network_in, network_out]` — **절대임계치가 탐지, Z-score/IForest는 기여 안 함**(z=0.58~0.82로 임계치 미달, IForest 일부는 0.36으로 단독이면 미탐). 이 시나리오의 "100% recall"은 임계치 컴포넌트의 성능이지 ML 모델 성능이 아님 — 보고서에 명시할 것.

## 2. 오버프로비저닝 (EC2, Resize)

- **독립변인**: CPU 사용률 수준 (목표 12% vs 45%)
- **통제 변인**:
  - 인스턴스 타입: **t3.small**로 통일(anomaly/normal 둘 다) — t3.micro를 쓰면 Resize 절감액이 항상 $0이 되므로 반드시 한 단계 위로 통일
  - 부하 생성 알고리즘: 동일한 duty-cycle(busy/idle 반복) 로직, **목표 %만 다름**
  - 네트워크 트래픽: 부하 생성이 CPU만 건드리므로 둘 다 낮게 유지됨(AND 조건 통제)
  - AMI/보안그룹/서브넷: 좀비 실험과 동일 조합 재사용
- **잠재 교란변수**:
  - duty-cycle의 **실제** CPU%가 목표%와 정확히 일치하는지는 실측 후 `raw_metrics.cpu_utilization`으로 검증 필요(가상화 오버헤드, 스케줄링 지연 등으로 오차 가능)
  - normal(45%)이 오버프로비저닝 상한(20%)에서 충분히 떨어져 있어 경계 근처 애매함은 없음 — 반대로 anomaly(12%)가 좀비 임계값(5%)과 상한(20%) 정중앙 근처인지도 실측 확인 필요
  - **정상 8개 데이터를 좀비 실험과 재사용 금지** — 같은 CloudWatch 구간을 두 번 세면 중복측정(pseudo-replication)
- **비용**: t3.small은 프리티어 대상 아님 — 13대×2.5h×$0.0210/hr ≈ **$0.68 실비용 발생** (이 세션 최초의 $0 아닌 지출)

## 3. 재시도폭증 (Lambda, Throttle)

- **독립변인**: 에러율 (고에러 45~90% vs 저에러 0~3%)
- **통제 변인**:
  - 함수 메모리/설정: `LAMBDA_FUNCTIONS` 목록의 13개 함수, 같은 런타임
  - 호출 간격: ±15% jitter를 의도적으로 줘서 "완전히 똑같은 반복"이 아니게 함(자연스러운 변동 포함이 오히려 통계적으로 더 타당)
  - 관측 기간: phase_minutes 기준 동일
- **잠재 교란변수**:
  - **계정 Lambda 동시성 한도(10)** — Throttle 액션이 실제로 실패해서 Action 성공률 0%가 나왔던 원인. 쿼터 증설 요청(10→1000, PENDING) 승인 확인 필요
  - 승인 게이트: cost_spike는 base risk가 항상 MED라 실제 운영에선 항상 승인 필요 — Action/QA 측정은 `--bypass-approval`(측정 전용)로만 가능
- **미해결**: 쿼터 승인 후 재실행 → Action/QA n 재확보 필요

---

## 4. 대량 다운로드 (S3, Block)

- **독립변인**: 다운로드 요청 수 / bytes_downloaded
- **통제 변인**:
  - 객체 크기: 50KB로 통일(원래 1MB였으나 실 AWS 전송량/비용 감안해 축소 — mock 학습 데이터도 동일하게 재생성함)
  - 버킷 설정: 13개 버킷 동일 설정
  - 관측 기간: 2.5시간 윈도우 동일(27 baseline + 3 spike 구조)
- **잠재 교란변수**:
  - IForest 콜드스타트/버퍼 상태 — 실측 중 1건 FP(정상 rep=5)가 IForest 경계값 아티팩트였음(z=0.66 정상, iforest 0.55 트리거) — 알려진 한계로 기록됨

---

## 5. EDoS 의심 (AutoScaling, ScaleDown)

- **독립변인**: `group_desired_capacity` 급증 여부 (capacity 1 → 3 이상)
- **통제 변인**:
  - baseline capacity: 정상 1로 통일
  - anomaly capacity: 3으로 통일(2.0배 초과 조건 충족 최소값)
  - 관측 기간: `--baseline-minutes 150`(창 전체) 미만으로 줄이면 안 됨 — 줄이면 창 앞부분이 0으로 채워져 탐지율이 낙관적으로 왜곡됨(스크립트 자체 경고)
- **잠재 교란변수**:
  - **계정 EC2 vCPU 한도(32)** — 기본 설정(n_anomaly=5×capacity3 + n_normal=8×capacity1 = 23대×2vCPU=46vCPU)이 계정 한도를 초과해서 두 번 다 setup 단계에서 중단됨. 쿼터 증설 요청(32→64, PENDING) 승인 확인 필요
  - 스크립트가 한때 팀원 커밋에서 실수로 빈 파일이 됐던 이력 있음(복구 완료, `git show 7c75522`에서 복원) — 복구본이 원본과 동일한지 재확인 권장
- **미해결**: 쿼터 승인 후 `--setup`부터 재시작 필요

## 실행 전 공통 체크리스트

- [ ] 해당 시나리오의 AWS 쿼터(vCPU, Lambda 동시성 등)가 필요량을 충분히 커버하는가
- [ ] IForest 모델이 동결 상태(`MOCK_SEED_BUFFER_FROZEN=True`)로 다른 시나리오와 동일한가
- [ ] anomaly/normal 그룹이 **독립변인 하나만** 다르고 나머지(인스턴스 타입, 관측기간, 부하방식)는 동일한가
- [ ] 이전 시나리오의 정상/이상 데이터를 재사용하고 있지 않은가(pseudo-replication 방지)
- [ ] 결과 파일에 실제 사용한 임계치/파라미터 값이 기록되는가 (재현성)
- [ ] 실험 종료 후 teardown(리소스 정리)을 실행했는가
