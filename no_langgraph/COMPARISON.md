# 3단계 — 순수 Python vs LangGraph 정량 비교

`langgraph_version/graph.py`는 `raw_python/`의 6개 stage 함수를 **그대로
재사용**하고, "언제/몇 번 부를지"만 `StateGraph` + `add_conditional_edges`로
다시 조립한 것이다. 즉 아래 비교는 "같은 로직, 다른 조립 방식"의 비교다.

실험 방법: 두 버전을 임시 디렉터리에 복사한 뒤 실제로 요구된 변경을
적용하고, `difflib.unified_diff()`로 실제 추가/삭제 줄 수를 셌다
(사람이 줄 수를 세거나 지어내지 않았다). 숫자를 낸 스크립트는 실험 후
정리했지만 이 문서의 diff 결과는 그 스크립트가 실제로 출력한 값 그대로다.

---

## 비교 1 — 코드 구조 (변경 전 기준)

**재시도/롤백 로직이 몇 개 파일에 걸쳐 있는가**

| | 순수 Python | LangGraph |
|---|---|---|
| 재시도 루프 자체 | `raw_python/orchestrator.py` 1개 파일 (`while True` 블록, 약 10줄) | `langgraph_version/graph.py` 1개 파일 (`qa_router` + `rollback_node` + `add_conditional_edges`, 약 15줄) |
| 롤백 실행 로직 | `raw_python/decision_action.py`의 `rollback_action()` (공유, 양쪽 다 씀) | 동일 |
| 재시도 임계값 상수 | `orchestrator.py`의 `MAX_RETRY` | `graph.py`의 별도 `MAX_RETRY` (값은 같지만 다른 상수 — 비교4 참고) |

파일 개수 자체는 이번 구현에서는 **거의 같다** (양쪽 다 "조립 담당" 파일
1개에 몰려있음). 차이는 그 안의 형태다: 순수 Python은 명령형 `while`
루프, LangGraph는 선언적 라우터 함수 + 그래프 등록.

**각 개발자가 "다른 사람 코드를 몰라도 되는 범위"**

두 버전 다 A(`detection.py`)와 B/C(`classification_qa.py`,
`decision_action.py`)는 서로의 내부 구현을 몰라도 된다 — 이건 orchestrator
든 graph든 "조립 담당 파일"이 알아서 조립해주기 때문에 **동일**하다.
차이는 조립 담당 파일 자체를 짜는 사람이 부담하는 몫이다:

- 순수 Python: 조립 담당자가 "정확히 몇 번째 줄에 다음 호출을 넣어야
  하는지"까지 알아야 한다 (실행 순서가 코드 줄 순서 그 자체이므로).
- LangGraph: 조립 담당자는 "이 노드 다음에 이 노드"라는 매핑만 선언하면
  되고, 실제 호출 순서는 그래프 엔진이 결정한다. 다만 라우터 함수 안에서
  `state.qa_passed`, `state.rollback_count` 같은 **필드 이름 자체는
  똑같이 알아야 한다** — 이 부분은 LangGraph를 쓴다고 없어지지 않는다.

## 비교 2 — 실측: "재시도 최대 횟수 2 → 3"

실제로 두 버전의 `MAX_RETRY = 2`를 `MAX_RETRY = 3`으로 바꾸고 diff를 쟀다.

| | 순수 Python (`orchestrator.py`) | LangGraph (`graph.py`) |
|---|---|---|
| 수정 파일 수 | 1개 | 1개 |
| 추가/삭제 줄 | +1 / -1 | +1 / -1 |

**결과: 이번 시나리오에서는 차이가 없었다.** 두 버전 다 `MAX_RETRY`를
파일 하나에 상수 하나로 뒀기 때문에(설계 단계에서 이미 신경 씀), 이
특정 변경은 LangGraph를 쓰든 안 쓰든 똑같이 쉬웠다. "LangGraph를 쓰면
숫자 하나 바꾸는 것도 무조건 더 쉬워진다"는 주장은 이 실험에서는
지지되지 않는다 — 순수 Python이라도 상수를 한 곳에 모아두면 똑같이
1줄로 끝난다.

(참고: DESIGN_NOTES.md 3번 항목처럼 애초에 상수를 한 곳에 모아두지
*않았다면* 두 곳 이상을 고쳐야 했을 것이고, 그건 순수 Python이든
LangGraph든 똑같이 나는 문제다. 즉 이 부분은 "프레임워크의 문제"가
아니라 "상수를 한 곳에 두는 습관의 문제"였다.)

## 비교 3 — 실측: "Detection과 Classification 사이에 화이트리스트 단계 추가"

실제로 두 버전에 `whitelisted` 필드 + `whitelist.py` 신규 파일 +
조립 로직 수정을 적용하고 diff를 쟀다.

| 파일 | 순수 Python | LangGraph |
|---|---|---|
| `state.py` (필드 추가, **공유**) | +3 / -0 | +3 / -0 (같은 파일 공유) |
| `whitelist.py` (신규, **공유**) | +16 / -0 (신규 파일) | +16 / -0 (같은 파일 공유) |
| 조립 담당 파일 고유 수정 | `orchestrator.py`: **+5 / -0** | `graph.py`: **+14 / -1** |
| 조립 담당 파일 고유 수정 **총합** | **5줄** | **15줄** |

**결과: 이번 시나리오에서는 LangGraph 쪽이 더 많은 줄을 고쳤다.**
`graph.py`가 `orchestrator.py`보다 3배 가까이 더 많이 바뀐 이유:
새 노드 래퍼 함수(`whitelist_node`, 2줄) + 새 라우터 함수
(`whitelist_router`, 2줄) + `add_node` 등록(1줄) + 기존
`add_conditional_edges` 블록을 2개로 쪼갬(순증가) — 선언적 방식은
"연결 하나"를 표현하는 데 필요한 보일러플레이트(함수 선언 + 등록 +
매핑)가 순수 Python의 "그냥 2줄 끼워넣기"보다 원래 더 길다.

**그런데 줄 수와 별개로, 실제로 확인해본 질적 차이가 있다:**

1. **삽입 위치의 안전성** — 순수 Python은 `orchestrator.py`의 기존
   함수 *본문 중간*에 새 호출을 끼워 넣어야 한다. 만약 `if not
   state.anomaly_flag: return ...` 블록보다 *앞에* 화이트리스트 체크를
   넣어버리면(순서를 착각하면) 이상 탐지 자체를 건너뛰고 화이트리스트만
   보게 되는 등, **아무 에러 없이 조용히 잘못된 동작**을 하게 된다.
   LangGraph 쪽은 새 로직 대부분이 *새 함수 2개를 추가*하는 형태라
   기존 함수 본문을 직접 헤집을 필요가 적다.

2. **연결 오타를 잡아주는가 — 실제로 확인함.** 존재하지 않는 노드
   이름으로 엣지를 연결하고 `compile()`을 실제로 실행해봤다:

   ```python
   graph.add_edge("a", "nonexistent_node")
   graph.compile()
   # ValueError: Found edge ending at unknown node `nonexistent_node`
   ```

   즉 그래프 배선을 잘못하면 **`compile()` 시점에 즉시 에러**가 난다.
   순수 Python에서 동등한 실수(함수 호출 순서를 잘못 넣는 것)는 아무
   에러도 안 내고 그냥 조용히 잘못 동작한다 — 이게 이번 실측에서 가장
   실질적인 차이였다. "줄 수가 적다"보다 "실수했을 때 알려주는가"가
   실제로 더 크게 갈렸다.

## 비교 4 — 버그 발생 가능성 (DESIGN_NOTES.md 3번 항목 재검증)

**질문**: "재시도 임계값이 여러 곳에 중복되면서 값이 어긋나는" 버그가
LangGraph 버전에서는 구조적으로 안 생기는가?

**답: 아니오, 이번 구현 그대로는 똑같이 생긴다.**

```python
# raw_python/orchestrator.py
MAX_RETRY = 2

# langgraph_version/graph.py
MAX_RETRY = 2   # 값은 같지만 import로 연결된 게 아니라 완전히 별개의 상수
```

LangGraph를 쓴다고 "상수를 한 곳에서만 관리하게" 자동으로 강제되지
않는다. LangGraph가 실제로 없애주는 건 **"재시도 반복 자체를 손으로
`while`문으로 구현하다 반복 조건을 잘못 옮겨 적는" 유형의 버그**다
(조건 판단이 `qa_router` 함수 하나에 모여 있고, 그 함수가 그래프에
의해 정확히 한 번씩 호출되는 걸 프레임워크가 보장하므로 — "루프를
도는 부분"의 정확성은 프레임워크 책임, "무엇을 판단 기준으로 삼을지"는
여전히 개발자 책임이다). 반면 **"같은 상수를 두 파일에 따로 정의해서
어긋나는" 유형의 버그는 LangGraph와 무관하게 여전히 사람이 조심해야
한다** — 이건 비교3에서 확인한 "연결 오타는 compile()이 잡아준다"와는
다른 종류의 문제라서, LangGraph의 안전장치가 커버하는 범위 밖에 있다.

## 비교 5 — 실측: "승인 대기(일시정지 → 나중에 재개)" 기능 추가

실제로 두 버전에 "위험도가 높은 액션은 승인 대기 상태로 멈췄다가, 나중에
승인되면 이어서 실행"하는 기능을 추가하고 diff를 쟀다. 이 기능은
`pipeline/graph.py`(실제 프로젝트)에도 그대로 시험 적용해봤던 것과 같은
설계다 (적용 후 확인만 하고 원복함).

**LangGraph**: `state`에 필드 추가, 기존 `while`/라우터 로직은 그대로 두고
새 노드(`approval_gate`) 하나 + `compile(checkpointer=..., interrupt_before=[...])`
만 추가.

**순수 Python**: `while` 루프는 "프로세스가 죽으면 사라지는" Python
콜스택 위에서 도는 것이라, 프로세스가 꺼졌다 켜져도 이어서 실행되게
만들려면 애초에 `while` 루프로 표현이 안 된다. "지금 어디까지 왔는지"를
문자열(`step`)로 외부화하고 그걸 보고 분기하는 명시적 디스패처로
**기존 로직을 통째로 재작성**해야 했다. 체크포인트 저장/로드도 직접
구현해야 한다 (LangGraph의 checkpointer가 대신해주던 부분).

| 파일 | 순수 Python | LangGraph |
|---|---|---|
| `state.py` (필드 추가) | +4 / -0 | +5 / -0 |
| 핵심 로직 파일 | `orchestrator.py`: **+61 / -25** (while 루프 → step 디스패처로 전면 재작성, 원래 54줄짜리 파일의 절반 가까이가 바뀜) | `graph.py`: **+16 / -3** (기존 while 루프/라우터 로직은 한 줄도 안 바뀜, 분기·컴파일 옵션만 추가) |
| 신규 파일 | `persistence.py` **+43줄** (체크포인트 저장/로드를 JSON 파일로 직접 구현) | `approval_gate.py` +18줄, `runner.py` +33줄 |
| **합계** | **+108 / -25** | **+72 / -3** |

**결과: 이번엔 LangGraph가 실측으로도 더 적게 고쳤다.** 그리고 단순히
줄 수 차이보다 **"기존 코드를 얼마나 재작성해야 하는가"**가 핵심이다 —
순수 Python은 원래 있던 재시도 로직(`while` 루프)의 절반 가까이를
갈아엎어야 했지만, LangGraph는 원래 있던 로직을 단 한 줄도 건드리지
않고 새 분기만 얹었다. 이건 비교2·비교3의 "단순 분기 추가"와는 성격이
다른 요구사항(상태를 외부에 영속화해야 함)이라서, 여기서부터 프레임워크가
대신 해주는 일의 무게가 실제로 드러났다.

(참고: 실제로 `pipeline/graph.py`에 적용해서 돌려봤을 때, 승인 후 재개해도
`action_agent.py`가 자체적으로 갖고 있는 `if requires_approval: return
pending_approval` 체크에 다시 걸려서 실제 액션이 실행되지 않는 문제를
발견했다. 이건 LangGraph의 한계가 아니라 `action_agent.py`가 "그래프가
멈췄다 재개된다"는 걸 모르고 자기 나름대로 같은 조건을 한 번 더 검사하고
있어서 생기는 문제로, 정식 도입 시 `action_agent.py`도 함께 조정이
필요하다.)

## 종합

| | 순수 Python | LangGraph |
|---|---|---|
| 재시도 임계값 변경 (실측) | 1파일 1줄 | 1파일 1줄 — **동일** |
| 새 단계 삽입 (실측) | 1파일 5줄(조립 담당 고유분) | 1파일 15줄(조립 담당 고유분) — **LangGraph가 더 많음** |
| 새 단계 삽입 시 실수 위험 | 기존 함수 본문을 직접 수정 (조용히 틀릴 수 있음) | 대부분 함수 추가 + 선언적 재배선 (배선 오류는 compile()이 즉시 에러) |
| 승인 대기(영속화) 기능 추가 (실측) | **+108 / -25**, 기존 재시도 로직 절반 가까이 재작성 | **+72 / -3**, 기존 로직 0줄 수정 |
| 상수 중복 버그 | 발생 가능 | **똑같이 발생 가능** (프레임워크가 안 막아줌) |
| 배선(연결) 오타 | 조용히 틀린 동작, 잡아주는 장치 없음 | `compile()` 시점에 `ValueError`로 즉시 감지 (실측 확인) |

**결론**: 단순 분기 추가(비교2·3) 수준에서는 "LangGraph가 코드를 더
짧게 만들어준다"는 확인되지 않았다(화이트리스트 삽입은 오히려 더
길었다). 하지만 **상태를 프로세스 밖에 영속화해야 하는 요구사항(승인
대기)이 생기자 실측으로도 LangGraph가 더 적게, 그리고 기존 코드를
훨씬 덜 건드리고 구현됐다** — 순수 Python은 원래 있던 재시도 로직의
절반 가까이를 갈아엎어야 했지만 LangGraph는 한 줄도 안 건드렸다.
즉 LangGraph의 이득은 "코드가 항상 짧아진다"가 아니라, **요구사항이
프레임워크가 대신 해주는 영역(반복 실행 보장, 배선 검증, 상태
영속화/재개)에 걸릴수록 격차가 커진다**는 쪽에 가깝다. 반대로 "값이
여러 군데 중복되는" 유형의 버그는 LangGraph를 쓰든 안 쓰든 개발자가
직접 단일 소스로 관리해야 한다는 점은 동일했다.
